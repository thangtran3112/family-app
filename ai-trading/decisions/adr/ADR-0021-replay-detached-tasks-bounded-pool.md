# ADR-0021 — Replay background work is detached, and the API pool is bounded

The practice replay API runs its slow prep and re-scan work on a **detached daemon thread**, never as a background task of the request, and every API connection carries a `lock_timeout` and an `idle_in_transaction_session_timeout` so a stuck lock holder can no longer take the whole pool.

**Why.** The thread clock makes every read of a day take a `FOR UPDATE` lock on the day-list row, and FastAPI closes a request's DB session only *after* its background tasks finish. A re-scan started on a running day therefore queued a background task that waited on the same row lock the request already held — a deadlock Postgres cannot see (the wait runs through Python teardown, not in the database). Every poll of the thread then queued behind the lock, each holding one of the 15 pooled connections and a worker thread, until every `/api/desk/*` route timed out. The production Postgres log showed the signature — 13 backends blocked on `replay_day_lists … FOR UPDATE` plus the idle-in-transaction holders, exactly the pool size — and the 524s cleared the moment the container was recreated.

**The decision.** Preps and re-scans run on a thread the request does not wait on (`api/replay.py` `_detach`), so the request session and its lock are released when the endpoint returns. The API engine adds `lock_timeout` (10 s — a stuck holder returns a plain 503 "busy · try again" with `Retry-After` instead of 500) and `idle_in_transaction_session_timeout` (5 min) so no future stuck holder can exhaust the pool. CLIs and jobs are untouched. The clock model (a constant gap to real time, no stop at the close/overnight/weekend, hand-over at each session start) is unchanged. Regression tests in `tests/api/test_replay_clock_wedge.py` reproduce both the re-scan-on-a-running-clock deadlock and the stuck-lock → 503 degradation with real per-request sessions.
