# 01s — Vibe long-run protection

**Date:** 2026-10-15 · **Status:** approved; implementation in progress · **Lane:** Trading Hub / Vibe fork. Follows [01n](01n-vibe-research-quality.md) §4 and [01r](01r-vibe-committee-gate-design.md); does not change the Family Desk.

## Intent and acceptance

Routine ai-trading deploys must not cut off a family member's multi-minute Vibe chat research or its automatic investment committee. New chat turns can briefly wait during a release, but ongoing research finishes on the current process. If research cannot finish within **60 minutes**, abort before changing active preferences, secrets, or Vibe/other app containers; keep the old release and existing app-group choices running. The one-time first-upgrade ingress barrier may temporarily recreate only the gateway using a staged Caddyfile override; an abort restores its old mount/container without changing the installed old Caddyfile. An unexpected restart shows an **amber Interrupted** state and gives the user a deliberate retry, never a green Done or an automatic replay. No live trades, paid data, new provider account, or cross-app runtime changes.

Protected finite work: `SessionService` chat attempts from admission through terminal reply, plus private automatic committee runs even when their parent chat has stopped waiting. Standalone/manual swarms, Alpha jobs, scheduled jobs, persistent live runners, and other app groups remain separate work; do not report them as deploy-protected. User-requested app-group stop is not a routine deploy and still follows its existing stop behavior. This scope is a default from the approved conversation; broaden only after a separate decision.

## Chosen approach

Add a small deployment-drain control to the running Vibe process, rather than polling persisted attempts alone or adding a blue/green stack. A passive `attempt.json` scan cannot close the race where a new request starts between the last check and Compose replacement. Blue/green would duplicate large app resources and complicate the shared VPS rollback. Keep the existing Compose, lifecycle lock, health check, rollback, and 30 GiB disk guard.

### Runtime admission and observation

- `SessionService` atomically flips an in-memory drain state under the same lock used for session admission. A new chat send while draining returns a retryable 503 **before** storing a user message or attempt; existing attempts, history, cancel, and SSE remain available. Count a reserved session even while registry construction has not yet marked its attempt running. A process restart clears the drain state.
- The control plane exposes only drain/start, status, and undrain to a loopback request inside the Vibe container, authenticated with its existing API key when configured. Explicitly deny that path in Caddy's catch-all Vibe proxy; reject non-loopback callers inside Vibe as a second boundary. No new stored secret, no prompt or run content in the response or deploy logs. Reuse standard auth/cross-site checks; do not let a family browser invoke drain. The deploy driver uses the existing container environment to authenticate without printing or passing the key as a command-line argument. An ephemeral lease token is never logged.
- Drained means **zero admitted chat attempts AND zero private automatic committees**. A private committee may continue in a daemon thread after its parent returns on the tool's wait budget, so parent count alone is insufficient. Cover the handoff from committee-thread launch to persisted private run and from running private run to terminal state without a zero-count gap. Query only the private committee store, never publish private IDs/reports; unreadable or inconsistent state fails the idle check closed. New committee work from a previously admitted chat is permitted and remains counted until terminal. Manually launched swarms do not enter this count.
- Use an expiring drain lease plus explicit release so CI cancellation or a killed SSH client cannot leave the old server rejecting new research forever. Only the deployment holder can renew/release its lease; an expired lease reopens admission. The driver verifies that the container it drained is still the one it is about to replace, and confirms the lease remains valid before the switch. A container change, lost control connection, unreadable status, or expired lease aborts rather than treating a missing count as zero.

### Deploy ordering and failure

Under the existing ai-trading lifecycle lock, identify the currently running Vibe container and current desired app-group state. Skip the wait when there is no running Vibe service or the group is intentionally disabled. For a running, selected Vibe, enter drain before modifying persisted choices, active secret/config files, or Vibe/other app containers. Poll counts to zero with a monotonic 60-minute ceiling, renewing the lease through any staging/pull delay until the current container is replaced. On timeout, release drain and fail this deploy with the previous release active. On any pre-switch failure or rollback, release drain on the still-running old container; if that fails, fail loudly with recovery instructions instead of claiming a clean abort. Success starts the new Vibe process undrained and preserves MiroFish `keep` and other groups' saved choices.

After idle, hold the existing Caddy admission marker across replacement, health checks and the saved-tag commit on **both** legacy and drain-capable releases. A new Vibe process starts undrained, so its ingress must not admit another chat until that commit is healthy; a failed health check rolls back while the marker remains. A pre-switch failure restores active files without redeploying Vibe (and restores only a previously running MiroFish if an operator stop already touched that group). Once the tag is committed, marker cleanup failure reports **applied but gated** and never rolls back over a new process that may accept research; the marker owner is not overwritten or blindly deleted.

**First rollout:** the currently deployed Vibe image lacks this control endpoint. Never treat a missing endpoint as zero active work. The same scoped phase's first replacement needs a temporary ingress barrier that rejects new chat POSTs **before** the active-attempt/private-committee preflight, leaves existing research running, and remains in force until replacement or abort. Caddy has `admin off`: activate the rule with a gateway-only Compose override mounting the staged Caddyfile under the lifecycle lock, not a hot reload or early replacement of the installed file; failure/timeout recreates the previous gateway from the unchanged installed Caddyfile. A quiet-window file poll *without* that barrier is insufficient. If the barrier cannot be enforced or the preflight is uncertain, hold the release; do not silently downgrade. Later releases use the runtime drain path. A Vibe-disabled installation needs no old-process barrier. This bootstrap exception is not permission to bypass the 60-minute policy.

### Unexpected restart and user retry

Keep existing startup reconciliation of pending/running attempts to a terminal `interrupted` reply and the SP4 sanitized response checkpoint. Persist **only sanitized tool names, status, and timing** during a run, after the committee gate has filtered its callbacks; do not persist arguments, previews, provider bodies, private committee IDs, or raw drafts for the interruption view. A recovered reply carries those durable, bounded progress entries. If the record is missing or incomplete, say actions may have occurred but are not fully known; never imply that retry is side-effect-free.

Hydrate `interrupted` distinctly from `failed`, `cancelled`, and `completed` in the Vibe chat timeline. Show amber Interrupted, recovered safe text if any, known completed actions, and a warning that retry can repeat actions. Bind retry to the original prompt saved on that interrupted `Attempt` (not a guessed adjacent chat bubble); the recovered reply carries an authenticated, run-linked prompt reference for the UI. An explicit confirmation re-sends that prompt in the **same session** through the existing send route, with the currently selected model/effort; it creates a new attempt, not a continuation of the old one. Disable double submission while pending; a 409/503 leaves the original interrupted row intact. If no original prompt can be identified, offer normal manual composition instead of guessing. No auto-replay on page reload, SSE reconnect, process restart, or deployment rollback. Existing US-stock committee and output gates apply again to the new attempt.

## Verification contract

1. **Fork backend:** race admission versus drain; a rejected send creates no message/attempt; previously admitted registry-build and agent tasks finish; private committee that outlives its parent and the pending-launch handoff block idle; corrupt private-store state and wrong/remote credentials fail closed. Lease expiration and explicit undrain reopen admission. Restart recovery shows only gated text and redacted progress, preserves true terminal replies across a write-order crash, and never re-executes an attempt.
2. **Deploy driver:** fake Docker/API cases cover idle, active-then-finished, a 60-minute timeout without active-file/container/preference changes, transport failure, lease loss, disabled/missing Vibe, staging error, rollback, and a replacement container race. Assert that other app-group choices, MiroFish state, and secrets are unchanged on abort. Test the first-release compatibility path explicitly.
3. **Vibe UI:** hydrated interrupted activity is amber rather than Done; warning and known actions are accurate; one explicit confirmation submits exactly one new attempt; missing prompt, 409/503, reload, and SSE reconnect do not trigger silent retries. No raw committee content appears in checkpoints, history, or the retry UI.
4. **Integration/delivery:** fork backend suite, TypeScript/Vitest/build, `test-deploy-firestore.sh`, full Bake and real-Caddy smoke per `AGENTS.md`. Exercise a locally controlled long run through a deploy wait and an unexpected restart, with no live trades. After scoped `dev` and `main` PRs pass CI, verify the live auth gate, all saved Running choices, drain/release/abort behavior without forcing an active production run to restart, and saved interruption/retry history. Positive Finnhub verdict/target remains unverified until its optional free key exists.
